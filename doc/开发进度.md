## 2026-11-10：1.4.5

| 模块 | 内容 |
|---|---|
| Boss 判定 | 由单条 `IBossDisplayData` 扩为三条：`IBossDisplayData`、`IEntityMultiPart`、类名含 `Boss`（`ProtectBossNamed`） |
| Boss 名单 | 匹配同时接受实体键、完整类名与简单类名；默认 42 项按模组分组 |
| 命名生物 | `ClearNamedHostile` 默认改为 `false`，任何带 `CustomName` 的生物都不再清理 |
| 排查命令 | 新增 `/neverlag bosses`，按类汇总世界生物并标记保护对象 |

### 实测（server2：Crucible 1.7.10 + Java 26，端口 25599）

| 场景 | 结果 |
|---|---|
| `/neverlag bosses` | 世界生物 7 只、3 类，其中 Boss 级 5 只；5 只暮色九头蛇标记为 ★ |
| `clear all` | 清理完成：2 只，耗时 101 毫秒，命名牌保留 2 只，Boss 保留 5 只 |
| 类名匹配 | 临时把 `EntitySheep` 写入 `Boss` 段并 `reload`，羊变为 ★；撤回后恢复原状 |

### 已知限制

- `/neverlag bosses` 最多列 80 类，超出时只输出剩余类数。
- 控制台 `summon` 无法生成部分模组实体（报「无法在世界外召唤实体」），无血条小 Boss 的判定只能通过名单标记间接验证。
- `ClearNamedHostile: false` 下，InfernalMobs 与 SpecialMobs 的自动命名生物永久保留，不会被清理。

## 2026-11-10：1.4.4

| 模块 | 内容 |
|---|---|
| 预警 | 新增 `WarningAt` 与 `WarningMessage`，默认提前 60、10 秒各播一条纯文本 |
| 计时 | 预警与清理合并为单个每秒任务，共用 `elapsed` 计数器 |
| 清理 | 到点无条件执行，不设数量阈值 |
| 排查命令 | 新增 `/neverlag who`，输出在线玩家与 `bukkit.broadcast.user` 订阅者 |

### 实测（`Delay: 40`、`WarningAt: [20, 10]`、`Debug: true`，用 RCON 召唤 5 只牛）

| 时间 | 日志 |
|---|---|
| 02:36:58 | 预警已播报（剩 20 秒，在线玩家 0，广播回执 2） |
| 02:37:08 | 预警已播报（剩 10 秒，在线玩家 0，广播回执 2） |
| 02:37:18 | 清理完成：5 只，耗时 51 毫秒，命名牌保留 1 只，Boss 保留 5 只 |
| 02:37:58 | 下一轮 20 秒预警按时重复 |

`/neverlag who` 在空服上的输出：在线玩家 0，`bukkit.broadcast.user` 订阅者 3
（`PermissibleBase`、`ColouredConsoleSender`、`CraftRemoteConsoleCommandSender`）。
`CraftServer.broadcast` 只对实现 `CommandSender` 的订阅者计数，`PermissibleBase` 被跳过，
所以同一时刻的回执是 2 而不是 3。

### 已知限制

- `broadcastMessage` 的返回值是送达的权限订阅者数，不是在线玩家数。空服实测回执为 2，
  来源是控制台与 RCON 发送者，因此日志中两个数分别输出。
- 修改 `Delay` 或 `WarningAt` 后必须执行 `/neverlag reload`，定时器在重载时重新挂载。

## 2026-11-10：1.4.3

| 模块 | 内容 |
|---|---|
| 简报通道 | 主路径改为 `player.spigot().sendMessage(BaseComponent[])`，与 `broadcastMessage` 同一底层包 |
| 次选通道 | `/tellraw <玩家名> <json>`，仅在服务端未实现 `Player#spigot()` 时启用 |
| 后备通道 | `Bukkit.broadcastMessage(纯文本)`，组件通道整体不可用时保证至少一行播报 |
| JSON 校验 | 由 `net.minecraft.util.ChatSerializer` 反射校验改为 `ComponentSerializer.parse`，不再依赖 NMS 类名 |
| 日志 | 区分通道数：`简报播报：N 名玩家（组件直发 x，tellraw y）` |

### 实测

| 场景 | 结果 |
|---|---|
| 离线组件探针 | 11890 字符 JSON 解析成功，19 个组件中 18 个带 `hoverEvent`，悬浮正文 48 行完整 |
| 空服 `clear all` | 日志出现「没有玩家在线，简报只写控制台」，无异常 |
| 游戏内显示 | 未做端到端验证：验证期间服务器无玩家，需要真实客户端确认悬浮与颜色 |

### 已知限制

- 1.7.10 的 Bukkit 没有 `Server.broadcast(BaseComponent)`（1.8 才加入），组件必须逐玩家发送，
  每名玩家一次调用，没有批量接口。
- 简报 JSON 由代码手工拼接，颜色从 `§` 代码解析成颜色名、`hoverEvent` 固定写 `show_text` 加
  `value` 字符串；组件对象只在发送前由 `ComponentSerializer.parse()` 生成。
- 降级链路较长（组件 → tellraw → 纯文本），排查时需要看 `Debug: true` 打出的 JSON 与通道日志。

## 服务端环境问题

1. **`Chunk.NoSpawnChunk` 与实体数**：`server2` 默认关闭无玩家区块的刷怪，无人时实体数会跳变，
   压力测试需在刷怪后立即执行清理，不能依赖自然累积。
2. **后台启动的 stdin 生命周期**：以 `sleep N | java ...` 方式后台启动时，`N` 用尽后管道关闭，
   Forge 控制台读 stdin 遇到 EOF 会持续输出「未知指令」，主线程被占满，调度器停摆。
   后台启动需给足时长，或直接使用 `gtnh启动.bat` 双击启动。
3. **启动进度判定**：stdout 重定向文件会先于 `logs/latest.log` 停止更新，
   判断是否启动完成以 `logs/latest.log` 中的 `Done (` 为准。

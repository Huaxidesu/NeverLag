# 注释与 Markdown 编写规范

> 适用于本仓库的源码注释、`doc/` 文档、`README.md` 与提交信息。
> 内容与同一工作区的其他 Minecraft 服务端仓库保持一致，第 6、7 节按本仓库的维护流程调整。

## 1. 写作原则

- 以读者完成理解或维护任务为目标，陈述事实、规则、原因和操作步骤。
- 使用准确、简洁、客观的表达；避免聊天语气、口头禅、感叹、反问和过程记录。
- 不写「我觉得」「我发现」「我们这里」「AI 已经」等第一人称或写作过程描述。
  需要表达项目决策时，写明决策本身及适用范围。
- 先给结论或用途，再补充背景、条件和例外；一个段落围绕一个主题。
- 术语、模块名、配置项、接口、路径和代码标识符使用项目正式名称，反引号标记代码标识符。
- 不重复代码或邻近章节已经说明且无助于理解的信息。

## 2. 源码注释

### 2.1 何时添加

- 解释意图、约束、非显然的业务规则、兼容性要求、边界条件或规避方案。
- 解释代码无法清楚表达的副作用、线程 / 生命周期要求、单位、取值范围或调用顺序。
- 对外 API、复杂算法和公共类型补充调用方需要的契约说明。
- 不为显而易见的赋值、分支、循环或 getter/setter 添加逐行旁白。

### 2.2 如何编写

- 注释说明「为什么」或「必须满足什么」，不复述「代码做了什么」。
- 注释与所描述的代码保持相邻；范围较大的说明放在类型 / 模块文档或本目录下。
- 使用完整清晰的句子，中文注释用中文标点；代码标识符、路径和命令保持原样。
- 注释必须与当前实现一致；修改行为时同步检查相关注释，删除过时说明。
- `TODO`、`FIXME` 写明事项与可识别上下文，禁止留下无说明的待办标记。
- 不在注释中记录调试过程、个人感受、提交日志或未经确认的猜测。

本仓库有多处与具体服务端版本绑定的规避代码（NMS 反射、聊天通道降级、`@a` 在 1.7.10 不生效等），
这类位置必须写明「为什么不能用更直接的写法」，否则后续维护者容易按直觉改回错误实现。

### 2.3 体量上限（针对大段落注释）

- 单条注释以 **1~3 行说清一个意图** 为常态；需要更长说明时上移到类型 / 模块文档或 `doc/`。
- 文件头注释不超过 **6 行**：文件用途、关键约束、必要来源；不写修改历史与背景故事。
- 禁止把文档级内容（教程式段落、设计论述、需求讨论）整段搬进源码注释。
- 单个类 / 方法的注释超过约 10 行，视为放错位置，应上移为文档。

## 3. 对话与提示词保密

- 注释、提交信息、文档中**禁止出现**与 AI 的对话内容或提示词原文（整段或片段）。
- 禁止出现过程性、对话性表述：「根据你的要求」「按指示」「你说」「我让你」
  「AI 建议」「助手认为」「本次对话」等——读者只需要决策与理由，不需要来源。
- 一律改写为决策与理由本身：
  - ❌ `// 用户说不能一直等着，加个后备处理`
  - ✅ `// 必须设置超时，避免无期限阻塞`
- 引用需求时写需求的结论与出处（版本变更记录、契约章节），不写讨论过程。
- 已推送历史中的泄露内容不做改写，随下次自然改动清除；未推送的立即清理。

本仓库为公开仓库，该条同时是发布前检查项。

## 4. Markdown 文档

### 4.1 结构

- 每份文档以唯一的一级标题开头，标题准确描述主题；标题层级连续，不跳级，不以加粗代替标题。
- 先写用途、适用范围和必要前提，再写步骤、细节、示例、限制或参考资料。
- 操作步骤用有序列表；并列事项用无序列表；字段对照用表格。
- 代码、命令、配置示例用带语言标识的围栏代码块；行内标识符用反引号。
- 相对链接优先指向仓库内文件，并确认目标存在。

`doc/` 下各文件的职责固定：

| 文件 | 内容 |
|---|---|
| `程序结构.md` | 项目定位、模块划分、数据流、配置结构、命令清单、判定规则、线程模型 |
| `开发进度.md` | 最近 3 次改动的模块清单、实测结果与已知限制，交接用 |
| `注释与Markdown规范.md` | 本文件 |

`README.md` 面向服务器管理员，只放功能、配置示例、构建、部署与验证结果；
设计细节与内部结构一律放 `doc/`，避免 README 随实现细节膨胀。

### 4.2 表达与格式

- 用简体中文；技术名词、API 名称和代码标识符按官方写法保留。
- 中文与英文、数字之间加一个半角空格（「TCP 端口 44444」）；中文句子用全角标点。
- 段落简短且主题单一；列表项语法平行；完整句以句号结尾，短语列表不加句末标点。
- 表格单元格保持简洁，复杂说明放到表格外。
- 不使用「如下」「见上」等依赖阅读位置的表达，给出明确标题或链接。

## 5. 用语对照表

写作与改稿时，避免左列口语、网络用语，按语境改用右列书面表述：

| 不写 | 改写成 |
|---|---|
| 兜底 | 后备处理、缺省逻辑、异常保护 |
| 踩坑、踩过的坑、坑 | 已知问题、注意事项 |
| 卡死、卡住 | 阻塞、失去响应；确认为死锁时写「死锁」 |
| 卡在 | 停留在、阻塞于 |
| 干掉、杀掉 | 终止、删除、结束进程 |
| 踢、踢下线、被踢 | 强制断开连接、断开连接 |
| 塞进、塞回、怼、扔进 | 写入、传入、放入 |
| 丢进、丢给、丢掉 / 抹掉 | 移交、传递 / 移除；数据丢失场景写「丢失」 |
| 砍掉、拔掉 | 移除、停用 |
| 跑通、跑一遍、跑过 | 验证通过、执行一次、已运行 |
| 起服、起服务、起不来 | 启动服务器、无法启动 |
| 停服 | 停止服务器 |
| 关掉、开着 | 停用、关闭、保持启用 |
| 开权限 | 授予权限 |
| 写死 | 硬编码 |
| 照抄、换成自己的 | 沿用、复制 / 改用自有 |
| 省得、省事 | 避免、以便 |
| 瘦包 | 精简包 |
| 搞定、弄好、搞 | 完成、处理 |
| 老服、老的 | 旧服务器、旧版本 |
| 撑爆、吃掉 | 超出上限、占用 |
| 对表 | 对照、核对 |
| 摸清、摸一下 | 确认、检查 |
| 压成一行 | 合并为单行 |
| 崩了、崩在 | 崩溃、崩溃于 |
| 炸了 | 出现异常、失败 |
| 顺手、顺带 | 同时、一并 |
| 打死不能 | 禁止 |
| 别 | 不应、不要 |
| 咱、你、我 | 删去主语，改为陈述句 |
| 收口 | 收敛 |
| 那条 / 我们自己那条 | 该条 / 本插件下发的 |
| 一眼能看出 / 看着像没做 | 可直接确认 / 表现为未生效 |

对照表无法穷尽所有口语表达；拿不准时按「书面、客观、可验证」的标准改写。

## 6. 提交信息

中文 Conventional Commits：

```
<type>(<scope>): <简述>

<正文：改了什么、为什么>
<实测：怎么验的、结果如何；未验证写明「未验证」>
```

- `type`：`feat`、`fix`、`docs`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`。
- `scope` 用模块名（`cleaner`、`report`、`config`、`nms`、`build`、`docs`）。
- 简述不超过 50 字，写明变更点；不用「更新」「优化」等无信息量表述，不加句号和 emoji。
- 正文写原因与影响，不写工作过程；过程由 git 历史承担。
- 提交信息同样遵循用语对照表与第 3 节。

示例：

```
fix(cleaner): 定时清理任务改用独立阈值开关

1.3.0 把 OnlyClearWhenLimit 的值写进 ClearEntity 总开关，ClearLimit 恒为 null，
OnlyClearWhenLimit 为 false 时清理任务根本不注册。现改为写入 ClearLimit，
并让 clean_run 仅在开关为真时判断阈值。

实测：server2 配置 OnlyClearWhenLimit: false，动物按 Delay 周期被清理。
```

## 7. 提交与上传

| 项 | 规则 |
|---|---|
| commit | 一个可独立说明的改动一个提交，不混无关改动 |
| push | 推送前用 `git log origin/legacy-1.3.0..HEAD` 核对范围，避免夹带无关改动 |
| 分支 | 在 `legacy-1.3.0` 维护，`master` 保留上游 2.0 源码，不改动 |
| 强制推送 | 不做；已推送历史不改写 |
| 产物 | `build/` 不进版本索引 |
| 版本号 | `build.sh` 的 `VERSION` 与 `plugin.yml` 的 `version` 同次修改 |

### 提交前检查

- 是否残留对话、提示词或「AI / 用户要求」类表述？
- 是否残留用语对照表中的口语表达？
- 注释体量是否超标（单条 > 3 行、文件头 > 6 行、类注释 > 10 行）？
- 注释是否与实现一致，文档的标题、链接、示例是否仍有效？
- 文中版本号、配置键、命令参数是否已核对？
- `doc/开发进度.md` 是否已更新到本次改动，且仍只保留最近 3 次？

## 8. AI 开发任务的时限

AI 执行开发任务前，为每个可能持续等待的步骤设置明确超时，并在开始前说明预计时限；
不得启动无期限的构建、测试、安装、网络请求或进程等待。

- 较大任务拆分为可检查的小步骤，每步设定时限；总任务较长时设阶段检查点并汇报进度。
- 达到时限未完成时停止或安全中断，记录已获得输出，先判断是正常耗时、资源不足、网络等待还是死锁。
- 只在确认仍有合理进展且能说明依据后，才可调整时限重试一次；不静默无限重试，
  不把仍在运行的任务报告为已完成，最终说明实际耗时、结果或阻塞原因。

本仓库的验证依赖真实服务端启动（`server2` 冷启动约 3 至 4 分钟），
启动、重启与压力测试必须给出时限，并明确超时后的处理方式。
